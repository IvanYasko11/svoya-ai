# СВОЯ AI

## Организатор задач — первый этап

Главный фокус: сначала личный организатор, затем выбор монетизации. Переезд и личный Reels архивированы как неактуальные. Пользователь общается только через ChatGPT; личные продажи и переговоры не предполагаются.

- Задачи: цель, следующий шаг, препятствие, приоритет 1–3, срок и статус.
- Фокус на сегодня: до трёх активных задач, сначала просроченные, затем приоритет.
- Хранение: localStorage в текущем браузере. Вход через Supabase Auth и облачная копия позволяют переносить список между устройствами. После согласования копий включено автосохранение локальных изменений с задержкой 800 мс; быстрое редактирование объединяется, изменения во время записи отправляются следом. Загрузка с другого устройства пока выполняется кнопкой восстановления.
- Вход не заменяет и не отправляет задачи автоматически. Автосохранение разрешается, когда проверенная копия совпадает с локальной, либо после явного сохранения/восстановления. При расхождении списков, сетевой ошибке, истечении входа или конфликте версий оно приостанавливается. События другой вкладки также приостанавливают автоматическую отправку. Автосохранение можно отключить флажком. Восстановление требует подтверждения и блокируется, если локальные задачи изменились за время запроса. Выход оставляет локальные задачи на устройстве; на общем устройстве нужно очистить данные сайта после экспорта.
- `organizer_backups`: одна копия на auth.users, RLS разрешает только собственную строку, anon не имеет доступа. Сервер увеличивает revision; PATCH с предыдущей версией предотвращает перезапись изменений с другого устройства. Нет service-role ключа в клиенте.
- Сессия аккаунта хранится только в памяти вкладки. После обновления/истечения сессии потребуется войти снова. Регистрация использует настройки подтверждения почты и лимиты Supabase; отправка почты на внешние адреса может требовать настройки SMTP. Пароль не сохраняется и не отправляется модели.
- JSON экспорт/импорт с проверкой схемы и явным подтверждением замены.
- Повреждённые данные не перезаписываются автоматически; конфликты вкладок блокируют устаревшее сохранение.
- Контекст обычного чата отправляется LLM только при включённом флажке. Архив и отложенные задачи исключены из советов чата. Ответ этого чата не изменяет список.
- Точные команды организатора выполняются локально без расхода LLM: добавление, завершение, откладывание, возобновление, архив, следующий шаг и приоритет. Свободные фразы разбираются отдельным `POST /api/organizer-plan` через текущий Provider Router. По нажатию «Разобрать» модели отправляются команда, локальная дата и выбранная карточка, либо до 60 задач без архива (включая отложенные для управления ими). Ограничение контекста 60 000 символов; большой список требует выбора карточки. Пароль, JWT аккаунта и служебные ID в сообщения модели не включаются.
- Выбор «К какой задаче» и кнопка «Дать команду» позволяют использовать «эту задачу» и различать одинаковые названия. Без выбора такие ссылки отклоняются; неизвестные и повторные названия не выбираются автоматически. Архивная карточка доступна свободному разбору только при явном выборе. Модель может просить уточнение или предложить создание/изменение до 10 карточек; удаление и выполнение внешних действий отсутствуют. Разбивка цели создаёт отдельные задачи, а не скрытые подзадачи.
- Сервер и клиент проверяют схему предложения: только поля карточки, известный однозначный адресат, допустимые значения. Предпросмотр показывает названия и каждое поле до/после; сохранение только по «Применить». Отмена, изменение команды, выбора или списка блокируют поздние ответы. Клиент также проверяет версию перед применением. Завершённый разбор останавливает индикатор; ошибка модели не меняет задачи. Применённое изменение запускает существующее автосохранение аккаунта.
- Новый API разбора проверяет JWT через Supabase Auth; без действительного входа LLM не вызывается. Истечение или отклонение сессии возвращает форму входа и останавливает отложенное автосохранение. На экземпляре API ограничены параллельный запрос и всплеск более 6 команд в минуту; это не общий лимит между serverless-экземплярами. Новый платный сервис или зависимость не подключены. Используется текущая модель, по умолчанию `openrouter/free`; при ошибке квоты нет обхода через другие free-модели того же аккаунта.
- Интерфейс: плавный CSS фон без библиотек, адаптация для телефона, поиск задач, быстрое завершение, раскрывающиеся редактор и резервные копии. Настройка reduced motion отключает анимацию.
- Автосохранение и восстановление на втором устройстве подтверждены пользователем. Следующий этап: проверить живой разбор свободной фразы в интерфейсе, затем закрыть авторизацию остальных API и выбрать следующий полезный инструмент.

Проверки: `node scripts/organizer.test.cjs`, `node scripts/organizer-ui.test.cjs`, `node scripts/organizer-proposals.test.cjs`, `node scripts/organizer-plan.test.mjs`, `node scripts/cloud-backup.test.cjs`, `node scripts/cloud-ui.test.cjs`, `node scripts/chat.test.mjs`, `node scripts/chat-ui.test.cjs`, `node scripts/provider-router.test.cjs`. Разбор модели проверяется подменённым ответом: валидная схема, уточнение, неоднозначность, инъекции, ошибки квоты и отменённые/устаревшие ответы. Эти тесты не подтверждают качество конкретной живой free-модели. Изоляция двух аккаунтов, запрет anon, серверная версия и устаревшая запись также проверены SQL-транзакцией с откатом тестовых строк.

Личный AI-оператор: User → Operator → Planner/Router → Risk Gate → Tool/Agent → Verifier → Repair → Memory → Result.

## Текущий этап

V1.7 — Provider Router + Planner.

### Реально работает

- Vercel Operator/API.
- Risk Gate HIGH/MEDIUM/LOW и подтверждение для опасных действий.
- Smart Router: GENERAL / WEB_RESEARCH / FILE_ANALYSIS / CODING_AGENT.
- Coding Agent через GitHub Actions + OpenCode.
- Safe Apply: изолированная ветка и Draft PR; main автоматически не сливается.
- Semantic Verifier и bounded Repair Loop до 3 попыток.
- Broker изолирует ключи провайдеров от дочернего Coding/Repair Agent.
- Provider Router: OpenRouter + Groq + Gemini + Mistral при наличии соответствующих ключей.
- OpenRouter account-level free quota распознаётся отдельно: при ошибке free-models-per-day система не тратит дополнительные запросы на другие модели того же аккаунта и переходит к другому настроенному провайдеру.
- Planner v1.7 возвращает структурированный план до исполнения и сохраняет его в Supabase tasks.
- Supabase memory/tasks и approval state.

## Почему V1.6 застрял

Мы сначала решали проблему как «плохая модель / нужен ещё один free model». Red Team показал другой класс ошибки: бесплатная квота OpenRouter привязана к аккаунту, поэтому переключение между free-моделями внутри OpenRouter не меняет лимит. Дополнительные retry при такой ошибке только расходуют квоту.

Исправление: Provider Router + классификация account-level quota, с fail-fast внутри провайдера и переходом к другому провайдеру.

Отдельно исправлена глобальная concurrency-группа GitHub Actions: теперь один task не отменяет другой task.

## Ключи провайдеров

GitHub Actions secrets:

- OPENROUTER_API_KEY
- GROQ_API_KEY
- GEMINI_API_KEY
- MISTRAL_API_KEY

Vercel Operator использует те же имена окружения только в серверной части. Секреты не хранятся в репозитории и удаляются из окружения дочернего OpenCode процесса.

## Проверки

Provider Router имеет отдельные Node unit tests в scripts/provider-router.test.cjs. Проверяются account-level quota, временный 429, переход на другой провайдер и non-retryable auth error.

## Ограничения, которые ещё не закрыты

- GitHub Actions job всё ещё имеет более широкие права, чем идеальная двухконтурная схема trusted/untrusted jobs.
- Авторизация аккаунта покрывает облачные копии и новый API разбора команд организатора. API обычного чата/Coding Agent пока не привязаны к аккаунту; approval cookie связывает подтверждение с браузерной сессией. Ограничитель нового API действует на экземпляр, а не глобально; открытая регистрация также не является списком разрешённых владельцев API.
- Shell-среда Coding Agent всё ещё обладает сетевой властью; broker уменьшает риск утечки ключа, но не заменяет sandbox.
- Semantic Verifier проверяет соответствие изменения задаче и структуру результата, а не фактическую истинность бизнес-утверждений.
- WEB_RESEARCH и FILE_TOOL пока представлены маршрутизацией/планом, а не полноценными исполнителями.
